# DCS-MCP — contributor guide for AI sessions

MCP server for DCS World: offline `.miz` authoring/inspection and a live-control bridge.
Driven by any MCP client (Claude, Codex, OpenCode). TypeScript, stdio transport,
`npm run build` / `npm test`.

## Layout
- `src/miz/` — `.miz` handling: `archive.ts` (safe zip read + copy-on-write pack),
  `lua.ts` (data-only Lua parser — never executes), `serializer.ts` (writes DCS Lua),
  `parser.ts` (canonical model), `authoring.ts` (mutations + trigger compiler),
  `resources.ts` (embedded files + `mapResource`), `frameworks.ts` (MIST/MOOSE/Skynet),
  `sessions.ts` (+ on-disk snapshots), `validator.ts`, `editing.ts` (remove/rename/move/update,
  statics, mission options), `projection.ts` (offline lat/lon), `templates.ts` (SAM sites).
- `src/data/reference.ts` + `data/*.json` — countries, unit types, theatres/airfields/parking,
  generated by `scripts/gen-reference-data.py` from pydcs. Never hand-edit the JSON.
- `src/tools/` — MCP tool registrations (`miz.ts`, `miz-authoring.ts`, `miz-editing.ts`,
  `reference.ts`, `bridge.ts`, `diagnostics.ts`) plus `resources.ts` (resources + prompts) and
  `position.ts` (x/y-or-lat/lon input). `src/guide.ts` is what CLIENTS see (server instructions +
  `dcs://guide/conventions`) — they never see this file, so put client-facing rules there too.
- `src/dcs/install.ts` — hook installer (`dcs_install_hook`, `dcs-mcp-server install-hook`).
- Version comes from package.json only (`src/paths.ts`); bump it there, in `server.json` and in
  `package-lock.json`. **PATCH bumps only** (0.6.x) until ATC lands in the MCP — the minor digit is
  reserved for that release, however large a change is otherwise.
- `src/bridge/client.ts` — TCP JSON client for the live hook.
- `scripts/Hooks/dcs-mcp-hook.lua` — live control hook. `scripts/Export.lua` — telemetry only.

## Ground rules
- Never execute mission Lua; parse it as data (`lua.ts` only evaluates literals).
- Never overwrite a source `.miz`; `saveSessionAs`/`packMiz` write a NEW file.
- Keep raw Lua doubly gated (`DCS_ALLOW_RAW_LUA=1` + `ALLOW_EXEC` in the hook).
- Every authoring change must round-trip: serialize → reparse → assert. Add a test.
- Be honest about what needs DCS/Mission-Editor verification; don't claim unverified behavior.

- CI (`.github/workflows/ci.yml`) runs build + test on Node 20/22/24 on Windows (DCS is Windows-only), a stock Lua 5.1
  job (incl. the compatibility matrix under the editor fix-ups), and a Linux job that regenerates the pydcs-derived
  data byte-for-byte from the sha256-pinned pydcs 1.0.0 wheel.

## Editing existing content (0.2.0) — offline-verified, NOT yet ME/flight-verified

- Removal checks trigger references (by id, via `document.triggers`) and refuses unless `force`.
- `removeTrigger` shifts every `trig.*[k>i]` down and recompiles. It REFUSES when a later trigger
  has a predicate with no compiler, or later `custom`/`customStartup`/`events` entries — their
  compiled Lua names its own index and we will not rewrite it from a guess.
- Renames never rewrite Lua; they report where the old name still appears.
- `moveGroup` translates units + group x/y + route point 1; rotates offsets about the lead.
- Waypoint 1 can never be removed (see the `fixUnitsPos` invariant below).

## Reference data, starts, statics

- `countryId` throws on an unknown name (it used to default to USA silently). `ensureCountry`
  refuses a country already on another side and keeps `mission.coalitions.<side>` in step.
- Aircraft `start`: point type/action and `airdromeId` / `linkUnit`+`helipadId` (ship) follow pydcs
  `Mission._flying_group_from_airport` / `flight_group_from_unit`. Parking choice mirrors pydcs's v2 rule
  (width/length/height fit + heli/aeroplane flag), skipping slots already used in the mission.
- New aircraft get `payload.fuel = String(fuelMax)` — string, as the flown e2e mission used.
- Statics follow pydcs `static_group`: one-unit group under `country.static`, `category` and
  `shape_name` from the catalogue, one empty route point.
- Forced-option keys/values: `FORCED_OPTIONS` in `editing.ts`, from pydcs `ForcedOptions`.
- Projection: Krüger 6th order; `tests/editing.test.ts` pins it to pyproj output (1 mm) and real
  airfield coordinates. If DCS moves a theatre origin, regenerate `data/` and re-check.
- SAM templates carry `provenance` (`engaged`/`me-saved`/`loaded`/`catalogue`). Only promote a
  template after it is actually flown; never upgrade provenance on reasoning alone.

Scene building (`src/miz/dressing.ts`): FARP statics follow pydcs `unit.py` (`category="Heliports"`,
`shape_name` FARPS/FARP/invisiblefarp, `heliport_frequency|modulation|callsign_id`); FARP starts link
`linkUnit`/`helipadId` to the pad like pydcs `flight_group_from_unit`. `occupiedParking` treats a
static within half a slot's width as occupying it, in BOTH directions (flights avoid statics,
`populateAirfield` avoids flights). Target grids, FARP support offsets and naval stations are our
conventions — do not describe them as editor-derived. `verify-mission.mjs` checks the trailing
column only for vehicle groups; ship groups may be formations.

To verify in DCS next: a parking/hot/runway/carrier start opening in the ME and spawning on the
ramp; a static of each category; forced options shown in the ME; one `catalogue` SAM (SA-10/SA-11)
engaging under Skynet; a helicopter cold start from a FARP and rearming from its support group;
statics parked by populateAirfield sitting on their slots with no spawn collisions; removing a trigger from an ME-saved mission and flying it.

## Countries, real-world inventories, mods

- `data/countries.json` `units` = what the ME OFFERS a country (pydcs countries.py). Permissive —
  never describe it as real-world. `countryOffers()` drives COUNTRY_TYPE_NOT_OFFERED (warning).
- `data/real-world-inventory.json` = Wikipedia equipment lists (`scripts/gen-real-world-inventory.py`,
  needs en.wikipedia.org; use `?action=raw`, the API endpoint is rate-limited).
- NO GUESSING in the inventory: a row matches a DCS type only when a designation (or, for
  unnumbered systems/ship classes, a name) appears LITERALLY in both the Wikipedia row and the
  pydcs id/name. Never add an alias from outside knowledge (Mirage->M-2000C, Mi-17->Mi-8, hull
  numbers->class were removed for exactly this reason). The only normalisation is notation
  (`F/A-` -> `FA-`). `exact` = same full designation; everything else is a family match.
- `autoAirWing` keeps a template squadron only if pydcs offers it to the country AND (when the
  country has a Wikipedia aircraft list) the country operates it. Dropped squadrons are reported.
- The same script writes `docs/real-world-inventory.md` (per-country summary). Coverage: 30/35
  countries; ships are weak (navy pages list major classes outside tables). Don't overstate it.
- `src/dcs/mods.ts` scans mod Lua as TEXT (never executes) for `make_flyable`, `add_aircraft` Name,
  `GT.Name` + `add_surface_unit`. Mods are STRICTLY ADDITIVE: `findUnitType` (pydcs) is always
  checked first, a mod re-declaring a stock id is ignored for it, search lists DCS first, and
  `installedMods()` never throws (unreadable folders yield fewer mods). Keep it that way: nothing
  that works with no mods installed may start failing because of a mod folder.
- Templates and air wings never swap a type for another; they skip and report.

## Session snapshots

`enableSessionPersistence()` (called by the server at startup, not by tests unless they opt in)
writes `<state>/<sessionId>/{source.miz, mission.lua, dictionary.lua, mapResource.lua, files/,
meta.json}` on every `refresh()`. `requireSession` restores a snapshotted id transparently.
Snapshot failures are logged, never thrown.

## Triggers: compiled runtime `trig` (DONE)

`addTrigger()` in `src/miz/authoring.ts` writes BOTH forms DCS uses:
- `mission.trigrules` — the Mission Editor's structured form.
- `mission.trig.{conditions,actions,func,funcStartup,flag}` — the compiled Lua the
  simulation runs. Triggers therefore fire when a generated `.miz` is flown directly.

`compileTrig(mission)` compiles every trigrule it understands and **leaves the compiled
entries of anything it does not understand exactly as they were** — never regenerate a
working trigger from a guess. It reports `{ compiled, skipped }` by index.

### Wiring, per trigger type (captured from ME-saved missions)
| type | `trigrules.predicate` | wiring | action suffix |
|---|---|---|---|
| `once` | `triggerOnce` | `func[i]` | `; mission.trig.func[i]=nil;` (self-disarm) |
| `continuous` | `triggerContinious` | `func[i]` | none |
| `change` | `triggerFront` | `func[i]`, latched via `trig.flag[i]` | none |
| `start` | `triggerStart` | `funcStartup[i]` | none |

`conditions[i]` is `return(<a> and <b> )` — note the single space before `)` — or
`return(true)` when there are no conditions. `actions[i]` joins calls with `;` and no
space. `trig.flag[i] = true` for every compiled index.

### Ground truth, not guesswork
Predicate signatures are DCS-internal and version-sensitive, so they are **captured, never
invented**. `tests/fixtures/trig-oracle.json` pairs each `trigrules` spec with the exact
Lua the Mission Editor compiled for it (66 predicates, 41 whole triggers covering all four
types). Regenerate it after a DCS version bump:

```
npx tsx tests/build-trig-oracle.ts "<Saved Games/DCS/Missions>" "<DCS>/Mods/aircraft" \
  "<DCS>/Mods/campaigns" tests/fixtures/trig-oracle.json
```

Several folders are allowed (the out path is last). Include ED's own campaign missions: a user's
folder is almost entirely `triggerOnce`, and the other three types' wiring would stop being
checked. Folders this project writes into are skipped automatically.

**Adding a predicate:** add it to the oracle's supported set, regenerate, confirm a record
appears, then write the builder in `conditionRule`/`actionRule` and the compiler in
`CONDITION_COMPILERS`/`ACTION_COMPILERS`. If no oracle record exists, do not add it.
`c_unit_alive` is deliberately absent for exactly this reason.

### Conventions the file format requires
- Triggers reference groups/units/zones by **numeric id**, never by name. The tool API
  takes names and resolves them; an unknown name throws instead of producing a dead trigger.
- `addTriggerZone` assigns a `zoneId` (see `maxZoneId`).
- Message text goes in `l10n/DEFAULT/dictionary` as `DictKey_ActionText_<n>`, where `n`
  comes from `mission.maxDictId` — one counter shared by every DictKey prefix.
- `a_end_mission` takes a `coalition.side.*` enum name, not `"blue"`.

### Tests
- `tests/trig.test.ts` — oracle match (byte-for-byte), `return(true)`, skip-preservation,
  idempotent recompile, type-change rewiring, emitted Lua parses.
- `tests/trig-runtime.test.ts` — loads an authored mission's triggers under DCS's own Lua
  (`luae.exe`) with mocked predicates and asserts real firing behaviour. Skipped unless
  `DCS_LUA` points at `<DCS>/bin-mt/luae.exe`.

### Verified in DCS (2026-07-25, Persian Gulf, DCS multithreaded)
An authored mission was loaded through the bridge and run. Confirmed live:
`triggerStart` and `triggerOnce` triggers fired at the right model times (`T3` at t=0,
`T2` at t=15) and their actions ran; the single `Load Scripts` start trigger loaded MIST,
MOOSE and Skynet in order and all three initialised; all 18 authored ground units reported
`LAND` from `land.getSurfaceType`.

A second sortie (same day, flown from the DCS mission list, ~26 min, player F-16 SEAD
against the SA-2) added the zone predicates:
- `part_of_coalition_in_zone` on a **`change`** trigger (`triggerFront`) — fired once on the
  false→true edge as the player crossed into `IngressZone` (t=37 and t=32 across two runs).
  This is the only live proof of the `trig.flag[i]` latching.
- `unit_in_zone` on a `once` trigger — fired on entering the SA-2 ring (t=184, t=153).

Two further sorties (18:44–19:07 local, same mission) fired `group_dead`:
`T7-Sa2Down` at t=231 and t=161. Its `set_flag`, coalition message and `once` self-disarm
all ran. `c_group_dead` is verified.

**`c_group_dead` does not track `S_EVENT_DEAD` one-for-one — do not use the event stream to
predict it.** In both sorties the trigger went true roughly a second after the last
`S_75M_Volhov` launcher died, while a radar unit still had not reported dead:
- sortie A: DEAD seen for Mike-3/4/5/6 (the four launchers) at t=230; Mike-1 (`p-19 s-125 sr`)
  and Mike-2 (`SNR_75V`) took HITs but emitted no DEAD at all. Trigger fired t=231.
- sortie B: DEAD for Mike-1/3/5/6 plus one whose name no longer resolved (`initiator=unknown`)
  at t=154, Mike-4 at t=160, trigger fired t=161 — and Mike-2 emitted its own KILL+DEAD 52 s
  later at t=213.

Whether DCS's group-dead check is launcher-weighted or simply leads the DEAD events cannot be
told from the log; what is established is that it fires earlier than a naive "count the DEAD
events" model predicts. Skynet's own `isDestroyed` is a third, later signal again — the site
read `dead=true` only at the t=180 sample, 19 s after the trigger.

Still unverified: `T8-Sa6Down` (the SA-6 was never engaged), the flag-ANDed win trigger
`T9-Success` and `end_mission` that depends on it, and the radio-menu handler `T4-Sitrep` —
that one needs someone to actually press the F10 item.

Clean across all sorties: 18/18 units `LAND` and zero `TERRAIN_WATER`, MIST 4.5 / MOOSE /
Skynet `ok=1` on every boot, `samSites=3 ewRadars=2` every time.

Not our bug, seen in this sortie: Skynet 3.3.0 raises `Weapon doesn't exist` at
`skynet-iads-compiled.lua:3179` (`SkynetIADSContact:getTypeName`) whenever a tracked contact
is a weapon that expires between the nil check on `getDCSRepresentation()` and the
`:getCategory()` call on the next line. It is raised from Skynet's own MIST-scheduled loop,
only while missiles are in the air, and it reproduced in every sortie. Nothing in this repo
calls that path.

## Resources, scripts and frameworks

`src/miz/resources.ts` embeds files under `l10n/DEFAULT/` and registers them in
`l10n/DEFAULT/mapResource` (`["ResKey_Action_N"] = "file.lua"`). Triggers reach them via
`getValueResourceByKey`. Resource keys come off the SAME `mission.maxDictId` counter as
dictionary keys — verified: a real mission carries `DictKey_ActionText_14` and
`ResKey_Action_15` side by side.

`MissionSession` carries `dictionary`, `mapResource` and `files` (a `Map<name, Buffer>`);
`saveSessionAs` writes all three. `packMiz` takes `string | Buffer` so binary resources
(`.ogg`, images) round-trip byte for byte.

### Framework load order is the whole problem
DCS walks `trig.funcStartup` with `pairs`, so SEPARATE start triggers have no defined
order, and Skynet dies if MIST is not loaded yet. Everything therefore goes into ONE
`triggerStart` commented `Load Scripts`, whose actions compile into a single ordered Lua
chunk. This matches the ME-saved Skynet/MOOSE demo missions under
`Saved Games/DCS/Missions/LUA Scripts` — check those first if the format ever seems off.

Auto-discovery must stay narrow: a loose `mist[_-].*\.lua` pattern matches MIST's own
`mist_DBs_*.lua` sample dumps and silently embeds 3 KB of nothing. Patterns match the
versioned single-file build only, and `resolveFrameworkPath` refuses an auto-discovered
file below `MIN_PLAUSIBLE_BYTES` (an explicit path is never second-guessed).

### Skynet returns proxy tables — iterate them with `ipairs`, never `pairs`

`SkynetIADS:getSAMSites()` and `getEarlyWarningRadars()` return a
`SkynetIADSTableDelegator`: a proxy that forwards method calls to its elements and carries
its own `__index` field. `pairs` therefore yields **one extra, non-site value**. Observed
in a running mission: 4 SAM sites and 3 EW radars reported for a mission containing 3 and
2, and the IADS sampler dying every 30 s with

```
attempt to call method 'isDestroyed' (a nil value)
```

`ipairs` and `#` walk the array part only and see exactly the real elements. This applies
anywhere Skynet hands back a collection — telemetry, setup scripts, and inline
`do_script` trigger actions alike.

### Trigger surface
Conditions and actions are listed in `authoring.ts`. Note two traps, both ground-truth:
- `c_start_wait_for_user` is named like a condition but DCS stores it in a trigrule's
  `actions` array. The oracle records a `role` per predicate for this reason — never infer
  it from the `c_`/`a_` prefix.
- `a_out_text_delay_g` (per-group message) DOES take a `start_delay`, like the other text
  actions — the old claim here that it takes 4 args came from too narrow a sample; see the
  0.6.1 section on optional arguments. `a_radio_transmission` stores MHz in the rule and emits Hz,
  and its argument count varies (8/10/11) with the fields the rule carries.

## Unit geometry

**Headings are RADIANS in the file, degrees in the API.** Verified across 17,367 real unit
headings: 99.6% fall in [0, 2pi). `headingRadians()` converts on the way out. Writing
degrees through is not a rounding error — 90 becomes 90 radians, i.e. roughly 117 degrees.

**Unit layout must be derived from the heading.** Units trail the lead along the heading
(`buildUnits`), spacing per category in `FORMATION_SPACING` (vehicles 20 m, matching the
editor's own convoys). The old fixed `x + 30, y + 30` offset strung every group out to the
north-east regardless of facing, which reads in the editor as a group sitting at 45 degrees
to its own direction of travel. If you see `56.57` in a spacing analysis, that is `40 * sqrt(2)`
— the fingerprint of exactly this bug.

Note DCS map axes: `x` is NORTH, `y` is EAST, so a heading's forward vector is
`(cos h, sin h)`. Also: if a group has 2+ route points the editor overwrites each unit's
heading from `atan2(p2 - p1)`, so an authored heading only sticks on a single-point group.

**Only route point 1 is `ETA_locked`.** That field is the editor's "fix time" checkbox.
`routePoint()` defaults it to false; `initialRoute()` passes true for the mission-start
point, and `addWaypoint` passes `etaLocked: index === 1` so it is still correct when the
appended point IS the start. Locking later waypoints pins each one to a computed arrival
time, which the editor shows as a red ETA the moment any earlier leg changes. Covered by
`tests/authoring.test.ts` — "only the mission-start point is ETA-locked".

**A SAM site is not N copies of one vehicle.** `addGroundGroup` takes an optional
`composition: [{ type, count }]` that puts mixed unit types in ONE group, laid out in
order along the heading (`spacingMetres` overrides the per-category default). Skynet finds
a site by group name and then looks *inside* it for a search/track radar and launchers — a
group of launchers alone registers with the IADS and never fires. Compositions are copied
from ME-saved missions, not invented; `demo-missions/skynet-test-persian-gulf.miz` has a
working one for every common site type.

## Terrain: never trust a coordinate you did not check

`dcs_check_terrain` (hook `land`) batches `land.getSurfaceType` in the mission environment
and is the only authoritative land/water answer. A ground group on water does NOT error at
load — the vehicles sit inert, which reads as broken AI, not as a bad placement. It needs a
mission running. Two ways to get a trustworthy coordinate:
- lift it from an ME-saved mission (the editor put a vehicle there, so it is land), or
- spawn something on the map and query it.
Do both when it matters: `scripts/dcs-mcp-telemetry.lua` re-checks every ground unit five
seconds into the mission and logs `TERRAIN_WATER` as an ERROR for any that are wet.

## Getting from a built .miz to a running mission

`dcs_load_mission` (hook `loadmission`) calls `net.load_mission`, which **swaps the mission
on an already-running session** — it is the server mission-rotation call (DCS's own
`common.lua` gates it behind `DCS.isServer()`). It does NOT start a mission from a cold
menu: verified on this install (DCS multithreaded), from a cold menu `net.load_mission`
returns nil and does nothing — no `onMissionLoadBegin`, no load — from BOTH the GUI render
tick and an `onSimulationFrame` tick (`onSimulationFrame` does fire at this install's menu,
so `simTicking` is true there; it still no-ops). There is no menu→mission API a Lua hook
can drive; a true cold start would need `net.start_server(settings)`, which hosts an MP
server and changes single-player semantics, so it is deliberately not used.

The hook therefore **refuses `loadmission` unless `phase == "running"`**, with a clear "no
mission is running" error, instead of reporting a phantom success. To go from a built `.miz`
to flying: start any mission once (fly it), then `dcs_load_mission` swaps in the authored
one. `net.load_mission` only takes effect on the simulation thread, so `loadmission` is held
for an `onSimulationFrame` tick like the mission-env commands (`needsSimThread`).

Loading is **asynchronous**: it returns before the mission is up, and a mission that fails
to open reports it in dcs.log and nowhere else. Poll `dcs_bridge_status` for
`phase: running -> loading -> running`, then read the log.

`dcs_bridge_status` sends the hook's `status` command, not `ping`, so it surfaces `phase`,
`missionEnv`, `simTicking` and `mission` — check `phase` BEFORE any mission-environment tool
or `dcs_load_mission`. It falls back to `ping` if `status` is rejected, so an older installed
hook still reports connectivity. `ping` alone only proves the socket answers: it returns
`{pong, time}` from the menu just as happily as from a running mission, which is exactly the
false positive that made mission-env tools fail with `attempt to index global 'timer'`.

## Live telemetry

`scripts/dcs-mcp-telemetry.lua` runs in the mission environment (load it last, after the
frameworks) and writes `[DCSMCP] <KIND> key=value ...` lines to dcs.log: framework presence,
the terrain audit, world events, player state, per-site IADS status, and `DCSMCP.trig(name)`
for triggers to call from a `do_script` action. That last one matters — a trigger that never
fired and a trigger that fired into a broken action are otherwise indistinguishable.

The log is the transport on purpose: it is the one channel that still works while the
mission is loading and after a script has blown up. `scripts/monitor-flight.mjs` tails it
incrementally alongside a bridge poll and maintains a small `digest.json`.

`scripts/build-e2e-mission.mjs` builds a full Persian Gulf test mission through these APIs;
`scripts/verify-mission.mjs` runs the offline acceptance checks (validator, ED's own
`fixUnitsPos`, compiled-trigger syntax, unit geometry) against any `.miz`.

## What DCS needs before a flight spawns (verified live, DCS 2.9.31, 2026-11-16/17)

- A flight starting at an airfield only spawns if its side OWNS the airfield
  (`warehouses.airports[id].coalition`); a ship/FARP start needs the base's
  `warehouses.warehouses[unitId]` entry. Missing → no player slot, spectator only,
  no error anywhere. `claimStartAirfields` (logistics.ts) fixes both; it never flips
  an enemy-owned airfield. Air starts are unaffected. A finite EMPTY aircraft stock
  also denies the spawn (that is the logistics feature working).
- The briefing (`DCS.getPlayerBriefing()`) returns nil unless the mission has
  `pictureFileNameB/R/N` + `descriptionNeutralsTask` AND the units carry
  `callsign`/`onboard_num`/`livery_id`/`psi` — bisected live; keep both.
- Ship groups need ~1 km spacing: at 120 m a Moskva's escorts collided and died at t=0.
- To test unattended: `DCS.exe --force_disable_VR --no-launcher <miz>` starts straight
  into the mission; the sim waits on the briefing until FLY is clicked. The display
  is 150 % scaled — use DPI-aware coordinates. Synthetic keys do not reach DCS.

## Two invariants the Mission Editor enforces

**Every group needs `route.points[1]`.** `me_mission.lua:fixUnitsPos` indexes it
unconditionally for any group that has a `route`, so an empty `points` table makes the
editor fail to open the WHOLE mission with `attempt to index field '?' (a nil value)` —
and nothing points at the group responsible. No ME-saved mission has an empty route.
`initialRoute()` seeds one at the spawn position; `validator.ts` reports
`GROUP_NO_ROUTE_POINTS` as an ERROR; `tests/fixtures/me-open.lua` runs ED's own
`fixUnitsPos` under `luae.exe` so this fails in tests, not in the GUI.

**Check the log after generating a mission.** `dcs_status` / `dcs_get_log_errors`
(`src/dcs/log.ts`) read `Saved Games/DCS/Logs/dcs.log`, which is the only error channel
that works when no mission is running — and the only place an ME load failure is reported.
The route bug above was found this way and nowhere else.

## The live hook
`scripts/Hooks/dcs-mcp-hook.lua` runs in DCS's GUI environment, which is **Lua 5.1**:
`load(string)` is invalid there (`loadstring` is the 5.1 API), and DCS reports the failure
as a single dcs.log line while the bridge silently never listens. Parsing the hook is not
enough to catch that class of bug — `tests/hook.test.ts` LOADS it under `luae.exe` with the
DCS globals stubbed and drives its callbacks. Keep that test passing.

The hook opens its socket when it LOADS, and services requests from two tick sources:
`onSimulationFrame` (mission only) and `Gui.AddUpdateCallback` (the GUI updater
UserHooks.lua drives the menus with — confirmed present in the hook environment on this
install). So the bridge answers in the menu and the Mission Editor. The GUI updater is not
a documented hook API: keep it defensive — registered only if present, pcall'd, and
dropped after repeated failures rather than risking the user's UI.

### `net.dostring_in('mission', ...)` only works on the simulation thread

**Verified on this install, DCS multithreaded.** Called from the GUI updater it does not
reach the mission scripting state — and it does not fail loudly. The snippet runs somewhere
that has no `coalition`, `timer`, `land` or `coord`, so with a mission demonstrably running
every mission-env command came back:

```
attempt to index global 'coalition' (a nil value)
```

**DCS 2.9.31 moved it again (verified 2026-11-16 with the hook's state probe):** the
scripting globals (`timer`, `coalition`, `env`, `trigger`) are in state **`server`**;
`mission` is now the trigger state (`a_do_script` exists, `timer` is nil). Even on the
simulation thread `mission` fails with `index global 'timer'`. `runIn("mission", …)`
therefore resolves the real state (`server`, then `mission`) per mission and logs it.
Note `getValueResourceByKey` lives in the trigger state, not the scripting state.

`MISSION_ENV_COMMANDS` in the hook lists the affected commands; `service(source)` holds
such a request until an `onSimulationFrame` tick dispatches it. Do not "simplify" that

## Mining the mission corpus: triggers, campaigns, compounds, reactive spawns (0.6.1)

Everything in this section came out of a sweep of every Mission-Editor-saved mission on this
machine — the user's three mission folders, the rest of `Saved Games/DCS/Missions`, and every
mission DCS ships under `Mods/aircraft`, `Mods/campaigns` and `Mods/terrains`. Two scripts
reproduce it and both must stay clean:

```
node --import tsx scripts/sweep-triggers.ts  "<missions folder>" ["<more>" ...]
node --import tsx scripts/sweep-validator.ts "<missions folder>" ["<more>" ...]
```

`sweep-triggers` recompiles every trigger and diffs against the Lua DCS wrote. Last run:
**3024 missions, 39025 trigrules, 29023 recompiled, 55842 of 58046 compiled strings identical
(96.2%)**. `sweep-validator`: **3023 missions, zero ERRORs**.

### The trigger surface roughly doubled, all of it oracle-backed

`tests/fixtures/trig-oracle.json` now holds **66 predicates and 41 whole triggers covering all
four types** (was 45 and 36). New conditions: `c_group_alive`, `c_unit_damaged`,
`c_all_of_group_in_zone`, `c_part_of_group_out_zone`, `c_unit_in_zone_unit`,
`c_unit_altitude_higher`, `c_unit_altitude_higher_AGL`, `c_unit_altitude_lower`,
`c_missile_in_zone`, `c_bomb_in_zone`. New actions: `a_explosion_unit`, `a_explosion_marker`,
`a_explosion_marker_unit`, `a_signal_flare_unit`, `a_out_picture_s`, `a_mark_to_all`,
`a_add_radio_item_for_coalition`, `a_set_ATC_silent_mode`, `a_shelling_zone`,
`a_zone_increment_resize`, `a_ai_task`.

- **`or` is a separator, not a predicate.** A bare `{ predicate = "or" }` entry in a trigrule's
  `rules` array makes the compiled chunk join with ` or ` instead of ` and `, so the editor's OR
  condition group comes out as `A and B or C and D`. `joinConditions` does this; an `or` with
  nothing on both sides is refused rather than compiled to broken Lua. It has no standalone Lua,
  so the oracle builder deliberately records no per-predicate case for it.
- **`c_unit_in_zone_unit`'s middle argument is a real zoneId**, checked against `triggers.zones`
  in every mission that uses it — it is the editor's moving zone (the zone gives the size,
  `zoneunit` carries it), not a radius.
- **The weapon selector of `c_missile_in_zone` / `c_bomb_in_zone` is four numbers the editor
  joins with dots** (`"4.4.11.125"`). What they mean is documented nowhere this project can read,
  so they are passed through and never generated. An older single-integer form exists; it has no
  oracle record, so it is refused and the existing compiled entry is preserved.
- **`a_ai_task`'s spec is `ai_task = {groupId, taskNumber}`** — the editor's AI TASK PUSH, which
  fires a group's n-th stored task. 215 uses in the corpus, the second most common action.

### Optional arguments: what the field decides and what it does not

The oracle's tie-break was wrong twice before the sweep settled it. Three different things are
going on and they must not be conflated:

1. **Field-driven.** `a_radio_transmission` stops after `start_delay` (8 args) unless the rule
   carries `mic_effects`/`squelch_effects` (10) and then `text` (11). `a_explosion_marker` and
   `a_explosion_marker_unit` add their `name` argument only when the rule has one.
2. **Always written.** The trailing `start_delay` of `a_out_text_delay(_s/_g/_u/_c)`,
   `a_out_sound(_s/_g)` and `a_end_mission` is emitted whether or not the rule carries the field:
   `a_out_text_delay` is 4-arg 3208+2635+... times against 3-arg 516+508, `a_out_sound` 2-arg
   against 1-arg by the same margin. **This corrects the old claim that `a_out_text_delay_g`
   takes no delay** — it does, and `message_to_group` now accepts `delaySeconds`.
3. **Not derivable at all.** `a_radio_transmission` appears with 11 AND 12 arguments, and
   `a_explosion_marker` with 3 AND 4, for specs whose fields are identical. That is a DCS version
   difference. The oracle records the corpus-majority shape plus every other shape seen for the
   same field set as `alternatives`, and `tests/trig.test.ts` accepts any of them by SHAPE for
   those predicates (exact string match everywhere else). Never "fix" a compiler to chase the
   longer form: it cannot be produced from the rule.

Smaller ground truths from the same sweep: a marker's `color` defaults to `"0"` when the field is
absent; a flare's `bearing` keeps its stored type (`"0"` as a string, `90` as a number) and so
does `c_start_wait_for_user`'s `flag_back` — forcing either to a number silently replaced a real
`"0"` with 999.

`tests/build-trig-oracle.ts` now takes SEVERAL folders (out path last) and skips folders this
project writes into (`EXCLUDED`): an oracle built from our own output would only prove the
compiler agrees with itself. It also takes trigger types in rotation, because a user's folder is
almost all `triggerOnce` and would otherwise crowd out the `triggerStart` / `triggerFront` /
`triggerContinious` cases whose wiring differs.

### Campaign files (`src/dcs/campaign.ts`) — first-party format, offline only

A `.cmp` is a plain Lua chunk assigning `campaign = {...}`; DCS loads it with `loadfile` +
`setfenv`. Parsed as data, never executed. The format AND the progression rules come from ED's own
installed code read as text: `MissionEditor/modules/me_campaign.lua` (`loadCampaign`, locale
fallback `name_<LOCALE>` then `name_EN` then `name`, `checkCampaignIntegrity`, `createNewGame`,
`chooseNextMission`) and `me_campaign_editor.lua` (`saveCampaign` via `serialize_simple2`,
`getNecessaryUnits`, `getTypePlayerUnit`, and the editor's defaults `interval = {0, 100}` and
`skipScore = 100`).

- Progression: `result > 50` or skipped goes to stage + 1 (past the last stage wins); `== 50`
  repeats the stage; `< 50` goes to stage - 1 (below 1 loses). In the new stage every mission whose
  `interval[1] <= result <= interval[2]` is a candidate and **DCS picks one at random**, so
  `stepCampaign` returns all of them instead of choosing.
- `createNewGame` opens with a random mission among those whose `interval[2] == 100`, else logs and
  takes mission 1. A stage with a score gap stops the campaign (`error: no mission chosen`), which
  is why `validateCampaign` walks 0..100 per stage and reports the gap as an ERROR.
- `necessaryUnits[type] = type` for the type of the first unit with `skill == "Player"`, planes
  before helicopters — ED's own derivation.
- Mission files are NOT copied. DCS resolves `directory .. file`, recomputing `fullpath` on load,
  so the `.cmp` must sit beside its missions; `checkCampaignFiles` reports the missing ones.
- All 64 campaigns DCS ships parse with zero findings and round-trip through our own builder.
  Nothing written here has been RUN by DCS as a campaign.

### Compound footprints (`src/miz/scene-import.ts`)

The built-in `TARGET_TEMPLATES` grids are our convention: the right objects in the wrong shape. A
real compound in an editor-saved mission has a perimeter (HESCO sections, sandbags, revetments)
and objects at individual headings. So they are measured instead: statics are clustered by single
linkage at `linkMetres` (60 m default), the frame is the cluster's MODAL heading, and every object
keeps its exact forward/right offset AND its own heading offset. `addSceneTemplate` rotates all of
it together.

Provenance is `imported`, the same weak tier as `site-import.ts`. **Nothing here ships as a
built-in**: a footprint belongs to whoever built the mission it came from, so imported templates
stay in the user's own template folder (`scene-*.json` beside the site templates).
`distinctHeadings` in a scan result tells you whether the source turned its objects individually —
1 means it was laid on a grid and is no better than our own.

### Reactive missions (`src/miz/reactive.ts`)

What community "dynamic" missions actually are, read off the corpus: `a_activate_group` is the most
used action anywhere in it (441 uses), fired at late-activated groups (477 of them) by zone and
`c_group_dead` conditions, with `a_ai_task` pushing stored tasks and `c_random_less` providing the
variety. `addReactiveSpawn` writes exactly that. A delay costs a flag: DCS has no delay on
`a_activate_group`, so the condition sets a flag and a second trigger fires on `c_time_since_flag`.

`dynSpawnTemplate` is a real group field (ED's Dynamic Slots) and the editor writes it on every
flying group, but **every mission in the corpus carries it `false`**. `setDynamicSpawnTemplate`
writes the boolean and claims nothing else; the reactive path is the tested one.

### Effect statics

`big_smoke` is the only effect object DCS offers — ED's own `Scripts/Database/db_countries.lua`
has `default_Effects = make_unit_list{ "big_smoke" }` with `smoky_marker`, `smoking_line` and
`dust_smoke` commented out. It is absent from the pinned pydcs catalogue, so `EFFECT_STATICS` in
`editing.ts` names it explicitly; `effectPreset` 1-8 is what editor-saved missions carry, and the
editor's own preset table (`udb.tblPresets`, which holds the labels and the default) is in no file
this project can read, so a preset is required rather than defaulted and the labels are not named.
`effectCourse` comes from `me_static.lua`. Statics also gained `livery_id` (aircraft and ships
only) and the group-level `hiddenOnPlanner` / `hiddenOnMFD`.

### Validator: two more severities were ours, not DCS's

`TASK_WAYPOINT_MISSING` (195 occurrences) and `DUP_UNIT_ID` (120) fire on missions **DCS itself
ships**, which fly. Both are now warnings whose messages say so. The rule stands: run
`scripts/sweep-validator.ts` before changing any severity, and keep the ERROR list empty.

To verify in DCS next: a written `.cmp` actually played through two stages and branching on score;
an imported compound opened in the ME and sitting where it was placed; a reactive spawn firing in
flight (zone entry and group-dead); `big_smoke` with each preset; an `a_ai_task` push moving an AI
group; `a_mark_to_all` showing on the F10 map; `a_out_picture_s` displaying.

## Install, mods and types learned from missions; first live run (0.6.2)

### What is placeable now, and where each answer comes from

Three sources, checked in this order, and the first two never shadow each other:

1. **The pinned pydcs catalogue** (`data/unit-types.json`) — authoritative, with fuel,
   dimensions, tasks, parking fit. Always wins.
2. **Installed mods** (`src/dcs/mods.ts`) — mod Lua scanned as TEXT, never executed.
3. **Types learned from missions** (`src/dcs/mission-learned.ts`) — the general fallback,
   registered through `registerTypeSource` in `reference.ts`.

`findUnitType` now returns `source: "bundled" | "learned"`. A **learned** entry proves only
that the id exists and which category DCS files it under: `fuelMax`, dimensions and tasks
are NULL, so `addAircraftGroup` writes no `payload.fuel` (DCS applies its own default) and
parking fit cannot be checked. Never fill those in from a guess.

### Why learning from missions is the only general answer

A sweep of the local corpus found **145 distinct unit types no catalogue here knows**, in
three kinds:

- **Stock DCS types newer than the pydcs pin**: `Oil rig` (195 units), the carrier deck crew
  (`Carrier LSO Personell`, `us carrier tech`), `FARP_SINGLE_01`, `AS32-p25`, `CV_59_*`.
- **Mods whose ids are unreadable.** The Su-35 mod registers its type from COMPILED Lua
  (`Entry/Su35s_encrypt.lua`, LuaQ bytecode). No text scan will ever find `Su-35S`; its
  `Config.lua` mentions the name but the registration is in the bytecode.
- **Mods not installed here at all**: `Su-30MKI` (34 CLSIDs on its pylons), `Su-30SM`,
  `Su-30MKM`, `J-20X`, `Rafale_C`, `B-21`, `A-4E-C`, `UH-60L`, `OH-6A`.

The CLSIDs on a mod airframe's pylons in a real mission are the closest thing to that mod's
own weapon list that this project can get, so they are recorded as `stores`. `missions` (how
many distinct missions carried the type) is the confidence measure — one is a typo, ten is
real. Tools: `dcs_learn_mission_types`, `dcs_list_learned_types`, `dcs_remove_learned_types`.
Nothing is written to the user's missions, and a learned pack lives in the user data folder,
never in this repo: the ids may be someone else's mod.

### Mod scanning: `GT.Name` without a registration call in the same file

`scanModFolder` required `add_surface_unit(` in the SAME file as `GT.Name`. Big mods split
the two — HighDigitSAMs defines one unit per file under `Database/Vehicles` and registers
them from a loader elsewhere — so **72 of its 162 units were invisible**, including every
S-300/S-400 launcher. A file that sets `GT.Name` and carries the rest of a ground-unit
definition (`GT.DisplayName`, `GT.WS`, or the `GT_t` helper) now counts on its own.

### A heliport type the catalogue does not list

`addStatic` refuses `category = "Heliports"` on purpose (it needs the ATC fields), and
`FARP_KINDS` only had the three built-ins, so `FARP_SINGLE_01` and the like could not be
placed at all. `addFarp` now takes `type` for any heliport static a registered source knows,
taking its `shape_name` from that source. Pad count is reported as 1 because nothing in a
mission file states it.

### An empty group is now refused

`addGroundGroup` with no resolvable types built a group with zero units — silently. That is
the one shape that looks fine in the file and does nothing in the mission, and it happened
because a site template id was passed straight to the authoring function instead of being
resolved to a composition first (which is the tool layer's job: `findSiteTemplate`).
`buildUnits` now refuses it and says what to pass.

### Unbundled theatres

`theatre()`'s error used to read as "unsupported". It now says what is actually missing:
units can be placed and a mission authored on any theatre (the theatre is just a string in
the file); what needs bundled data is airfield lookup and lat/lon conversion, and an
installed theatre pydcs never exported gets those from `dcs_airbase_build_pack`.

### First live DCS run — see docs/verification.md for the full record

`scripts/build-verify-mission.mjs` builds a mission carrying eleven never-tested features;
`DCS.exe --force_disable_VR --no-launcher <miz>` starts straight into it. The run confirmed
the hook, the mission loading, `land` / `roads` / `los` / `clearspot` / `airbases`, an
airbase pack of 30 airfields, a terrain pack that **matches `dcs_check_terrain` to 0.003 m**,
and ordered script loading from one start trigger.

It also found a real bug: **`DisembarkFromTransport` does not exist for DCS.**

```
ERROR WORLDGENERAL: "ComboTask" unable to create task "DisembarkFromTransport"
```

Hoggit documents it; the editor writes `Disembarking` with `{x, y, groupsForEmbarking}` and
no radius. The corpus is unambiguous — `Disembarking` 58 occurrences including missions DCS
ships, `DisembarkFromTransport` zero — and `transport.ts` now writes that. **Hoggit
documents the scripting API; what the ComboTask factory accepts is a different list.** When
the two disagree, the editor's own output wins.

Two corrections the live data forced on `airbase-packs.ts`: DCS's parking `termType` IS
returned (the docs said it was not) but it is a DIFFERENT enum from pydcs's `flags` — live
104/72/16 against bundled 6/4 on the same airfield — so it is stored and never mapped; and
`Term_Index_0` comes back as `-1` when absent, which was being written as the parking id.

What still needs a human: the sim waits at the briefing until FLY is clicked and synthetic

`net.load_mission` through the bridge also no-ops from that paused state, one step further
in than the cold-menu no-op already documented.

### Mod-manager repositories, and what "installed" actually means (0.6.3)

Mods live in two different kinds of place, and conflating them produces a mission
that looks fine and spawns nothing:

- **Deployed**: `Mods/aircraft` or `Mods/tech`, under a Saved Games profile or the
  install. DCS loads these, so their types spawn.
- **Available**: a mod-manager repository. OvGME keeps one folder per mod holding
  the tree it would deploy — `Saved Games/_OvGME Offline Mods/F-22A/f-22a/...` —
  and those mods are not enabled.

`modRepositoryRoots()` finds repositories beside the Saved Games DCS profile by
shape (`ovgme`, `jsgme`, `downloaded mods`, `mod repo` in the folder name);
`DCS_MCP_MOD_REPOS` (a path list) overrides the search for a different layout.
On this machine that found **four repositories, 30 available-only mods, 269 units**
that `Mods/` knew nothing about: an F-22A, an F-23A, a J-20, a Rafale pack, the CJS
Super Hornet, VSN F-35s, a Civil Aircraft Mod, and a 166-unit naval/SAM asset pack
(`Type055`, `CH_HQ22_STR`, …). 174 units are deployed, across 5 mods.

`InstalledMod.deployed` and `findModUnit(...).deployed` carry the distinction, and a
DEPLOYED mod always wins the same type id (`F15EX` resolves to the live copy, not the
repository one). A repository mod's units are filtered against the deployed set first,
so the two never double-count.

#### The validator now separates four different answers for an unknown type

Only the BUNDLED catalogue ends the question. A type that resolves because it was
learned from a mission is evidence the id is real, NOT evidence it will spawn here,
so the mod check still runs after a learned hit — otherwise a learned id silently
hides an undeployed mod.

| situation | code |
|---|---|
| in the pinned pydcs catalogue, or an effect static | (nothing) |
| declared by a mod DCS loads | (nothing) |
| declared by a mod sitting in a repository | `MOD_NOT_DEPLOYED` |
| learned from a mission, nothing here declares it | `TYPE_NOT_ON_THIS_MACHINE` |
| nothing knows it at all | `UNKNOWN_UNIT_TYPE` |

Across the local corpus that turned **265 `UNKNOWN_UNIT_TYPE` into 0**: 184
`TYPE_NOT_ON_THIS_MACHINE` (real ids from other people's mods), 16
`MOD_NOT_DEPLOYED` (mods sitting in the OvGME repository), the rest resolved. The
file is fine in every case — these stay warnings.

`countryOffers` is now consulted for bundled types only. pydcs lists what the editor
offers for the types pydcs knows; it cannot know a mod type, and reporting every one
of them as "not offered to any country" said nothing (it had inflated
`COUNTRY_TYPE_NOT_OFFERED` from 64 to 124).

### The Mission Editor ships its own template library (0.6.3)

`MissionEditor/data/scripts/templates.lua` is a plain `templates = {...}` assignment holding
the batteries the editor offers from its template list — **66 of them** on this install,
including `SA-2 SAM Battery`, `SA-2 SAM Battery (early)`, `SA-2 SAM Battery Iran`, the
Patriot, Hawk, NASAMS, S-300/S-400 and Rapier sites. `src/dcs/me-templates.ts` parses it as
DATA (never executed) and `allSiteTemplates()` serves it under `me-<name>` ids, read from the
install at call time and never vendored. On a machine with no DCS it contributes nothing, so
no built-in may depend on it.

This is first-party geometry and it beats anything assembled here from a reference diagram.
ED's `SA-2 SAM Battery` is 15 units: Fan Song at the origin, six `S_75M_Volhov` on a
**92-107 m ring**, `p-19 s-125 sr` 177 m out, two `ZIL-131 KUNG` vans at ~54 m, and a
power/fuel park behind. The built-in `SA-2` (4 launchers in a column) stays as it is — it has
`engaged` provenance and that is worth keeping — but new work should prefer the editor's.

**A site is not a formation of identically-aligned vehicles.** Every unit in ED's template
carries its OWN `heading`: the six launchers each point outward along a different bearing.
`SiteTemplate.headingOffsetsDegrees` and `buildUnits`' `headingOffsetsDegrees` carry that
through, as degrees relative to the group heading, so the whole site rotates as one. The old
rule that every unit shares the group heading was ours, not DCS's, and `verify-mission.mjs`
now enforces it only for a trailing column; for an explicit layout it checks the value is
radians and nothing more. (The editor still overwrites unit headings from the leg when a
group has 2+ route points, so these only stick on a single-point group — unchanged.)

`registerTypeSource`-style layering applies: a built-in id always wins, then the editor's
library, then the user's imported templates.

### Splash Damage is a registered framework (0.6.3)

`FRAMEWORKS.splash` embeds the community Splash Damage script (stevey9062) in the same single
`Load Scripts` start trigger, after MIST/MOOSE/Skynet. It does NOT require MIST — 3.4 Standard
contains no `mist.` call. Patterns match only the assembled release builds, never the ~132 KB
`Splash_Damage_main.lua` pre-assembly source, backed by a 200 KB floor.

**The three builds of a version are the same 7697 lines apart from three option flags**, so
the file NAME is all that separates them and discovery must not pick by sort order:

| file | smokeandcookoffeffectallvehicles | GU_Explode_on_Death | track_groundunitordnance |
|---|---|---|---|
| `Splash_Damage_<v>.lua` | false | false | false |
| `Splash_Damage_<v>_Standard.lua` | **true** | **true** | false |
| `..._Standard_With_Ground_Ordnance.lua` | **true** | **true** | **true** |

The patterns are ordered so the maintainer's own `_Standard` build wins: without it, vehicles
outside the script's cargo table get no secondary effects at all, which reads as the script
not working. Ground-unit ordnance tracking is the heavier opt-in and is never assumed — pass
an explicit path for that one or for the bare build. Discovery adds ONE
named root, `Missions/DCSSplashDamageScript-master` (the GitHub zip's folder); `Missions`
itself is deliberately not scanned, or a copy inside somebody's extracted `.miz` would win.
Verified live: `SPLASH DAMAGE 3.4 SCRIPT RUNNING` in dcs.log. The acceptance package embeds it
too and records `splashDamage: { embedded: false, reason }` in `manifest.json` on a machine
that does not have it, rather than silently shipping different missions.
